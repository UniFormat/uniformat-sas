# Feuille de route du driver Rust `sas7bdat`

Conception du 2026-10-30 (changement `design-rust-driver`). Chaque jalon a un critère de fin **mesurable** sur le corpus de `corpus/MANIFEST.md`, sur la matrice de `rea_output/tools/write_matrix.md` ou sur des benchmarks, et nomme les ADR de `docs/adr/` qu'il met en œuvre. Les seuils de performance sont des **objectifs à confirmer** par la première mesure ; aucun chiffre n'a été mesuré à ce jour.

## Préalable (hors jalons) — J0 : socle du dépôt

- Contenu : workspace Cargo (crates vides de l'ADR 0001), CI (stable et MSRV, `clippy` avec lints de l'ADR 0007, `cargo-deny`, `cargo tree` contre la liste de dépendances du cœur), `CONTRIBUTING.md` (règle de lecture des sources de `00` §5.1), harnais de tests d'intégration (`UNIFORMAT_CORPUS`), génération du CSV de référence par nom de colonne.
- Critère de fin : `cargo test --workspace` passe sur des tests vides ; l'arbre de dépendances du cœur est égal à la liste de l'ADR 0001 ; la MSRV est fixée d'après la MSRV de `arrow` et `datafusion` lue à ce moment (ADR 0007).
- Dépendances externes : décision NULL sur la publication (blocage `STATE.md`) — **n'empêche pas de développer en dépôt privé**.
- **Réalisé le 2026-11-02** : workspace de 9 crates (`crates/` : les huit de l'ADR 0001 plus `uniformat-testkit`, jamais publié), `rust-version = 1.97` (stable 1.99 − 2, au-dessus de `arrow` 60 = 1.88 et `datafusion` 55 = 1.94), lints de l'ADR 0007 en `deny` dans le cœur, `ci/check_core_deps.sh` (dépendances directes du cœur = `thiserror`, `encoding_rs`, `memchr`, aucune crate interdite sur 13 crates), `deny.toml`, `.github/workflows/ci.yml` (stable, MSRV, `cargo-deny`), `CONTRIBUTING.md`, licences `LICENSE-MIT` / `LICENSE-APACHE`, harnais `UNIFORMAT_CORPUS` (inventaire des **232** fichiers de `files/` et `external/`, CSV lus par nom de colonne, comparaison à `1e-13`). Vérifié en local : `cargo test --workspace`, `clippy --all-targets` (0 avertissement), `cargo fmt --check`, `cargo deny check licenses bans sources`, test d'inventaire sur le vrai corpus. **Non vérifié** : la CI hébergée (aucun dépôt distant), la compilation avec la toolchain 1.97 exacte (seule la stable 1.99 est installée), `cargo deny check advisories`.
- Constats du J0 : (1) les CSV de `files/` ne sont pas tous en UTF-8 (encodage de la table) : le harnais lit des octets, repli Latin-1 sans perte ; (2) le volume du projet ne gère pas le verrouillage de fichiers, d'où `incremental = false` dans `.cargo/config.toml`.

- Critère de fin :

  4. lignes supprimées : `suppression_n100_del10_no` donne 90 lignes visibles.
- Livraison : aucune publication.
- **Réalisé le 2026-11-03** (`crates/uniformat-sas` : `HeaderParser`, `MetaScanner`, `PageDecoder`, `RowRef`, `Limits`, `ReadReport` ; `crates/uniformat-sas-io` : `ByteSource` tranche/fichier, `SasFile`) :

En remplacement partiel : 3 196 entrées corrompues (octets mutés dans l'en-tête et les premières pages, troncatures) sur 47 fichiers du corpus, **aucune panique** (`tests/robustness.rs`) ; le critère « 1 heure CPU » reste **ouvert** ;

## J2 — Compression

- Contenu : `compress::detect`, `rle_decompress`, `rdc_decompress` (`15` §3 et §4), lecture des lignes compressées par pointeur `comp = 4` et lignes brutes, pages `0x9000` ignorées, `rle_compress` / `rdc_compress` (cœur, utilisés au jalon 6).
- ADR mises en œuvre : 0006 (C03–C09), 0001.
- Critère de fin :
  1. les **30 tables réellement compressées** du corpus (15 RLE, 15 RDC) et les **21 fichiers publics compressés** sont lus avec 0 écart ;
  2. les **338 + 367 vecteurs** de test (`15` §6) passent : `decompress(stocké) == brut` pour tous les vecteurs avec ligne brute connue, décompression sans erreur pour les autres ;
  3. `proptest` : `decompress(compress(x)) == x` pour 10⁶ lignes aléatoires et structurées, RLE et RDC ;
  4. `fuzz_rle` et `fuzz_rdc` : 0 panique, écriture jamais au-delà de `row_length` ;
  5. les 96 tables dont SAS a désactivé la compression se lisent comme des tables ordinaires.

- **Réalisé le 2026-11-04** (`crates/uniformat-sas/src/compress.rs`, `PageDecoder::visit_rows`) :
  1. **45 tables compressées** avec CSV lues avec **0 écart** (30 tables de `files/` et 15 fichiers publics datareader/pandas) ; les 7 autres fichiers compressés n'ont pas de CSV et se lisent sans erreur avec le nombre de lignes de RowSize (232 fichiers, 52 compressés, 204 055 lignes) ; les 96 tables dont SAS a désactivé la compression sont des tables ordinaires (comprises dans les 173) ;
  2. **705 vecteurs** (338 RLE + 367 RDC) : `decompress(stocké) == brut` pour 260 + 236, décompression sans erreur pour 78 + 101, 30 lignes brutes identiques, aller-retour du compresseur sur les 705 ; l'encodeur RLE reproduit les 260 flots de SAS ;
  3. **`proptest`** : `decompress(compress(x)) == x` sur 4 000 lignes aléatoires et 4 000 structurées par `cargo test`, et **10⁶ lignes par algorithme** (`-- --ignored`, release, 20 s), RLE et RDC ;
  4. **fuzzing : non exécuté** (nightly absent). Cibles `fuzz_rle` et `fuzz_rdc` écrites ; en remplacement partiel : 300 000 flots arbitraires et 40 000 flots valides mutés, aucune panique ; l'écriture ne dépasse jamais `out` (type `&mut [u8]`) ;
  5. les 96 tables à compression désactivée se lisent comme des tables ordinaires.
- Constats du J2 : (a) le bit 3 de l'octet de compression marque une ligne supprimée (C09, deux fichiers `readstat`) ; (b) `test2.sas7bdat` (jeu A) a le même nom que `test2.csv` (jeu B) : l'appariement par `EXTERNAL.tsv` prime ; (c) les fichiers datareader du jeu B portent le code d'encodage 29 ou 62 (U22) : `encoding_override` UTF-8 ; (d) la page `0x9000` termine le balayage des métadonnées.

## J3 — Métadonnées, formats et encodages

- Contenu : table de classification de `30` §1 (241 noms) embarquée et générée, `LogicalType`, conversion des époques (date, datetime, heure), table des 127 codes d'encodage et politique d'octets invalides (`30` §6), horodatages et release de l'en-tête (`10` §2.2), `TableMeta` complète exposée en Rust.
- ADR mises en œuvre : 0003 (décisions 1 et 3 hors Arrow), 0006 (F01, F04–F06, F10–F12, U22).
- Critère de fin :
  1. la table de classification attribue un `LogicalType` à **chaque nom** de la liste (241), test de complétude automatique contre `30` §1 ;
  2. texte décodé **identique** à `PROC PRINT`/CSV pour les 50 fichiers non UTF-8 du corpus (latin1, wlatin1, Shift-JIS) ;
  3. `Date32`/`Timestamp`/`Time64` : les valeurs de `PUT(valeur, format)` de l'oracle sont retrouvées sur l'échantillon de dates de `30` §4.4 (hors plage 1582…20 000 : `OutOfRange` rapporté, jamais silencieux) ;
  4. octets invalides : les trois lignes de `enc_inv` se relisent octet pour octet en mode `Binary` et avec un compteur en mode `Replace` ;
  5. 0 avertissement inattendu sur les 232 fichiers analysés (liste d'avertissements attendus versionnée).

- **Réalisé le 2026-11-04** (`formats.rs`, `temporal.rs`, `encoding.rs`, `page.rs` ; tables générées par `ci/gen_tables.py` depuis `30` §1, §1.1 et §6) :
  1. **classification complète** : les **241** couples nom/sens de `30` §1 et les **388** de §1.1 reçoivent un `LogicalType` (`Number`, `Date`, `DateTime`, `Time`, `Text`) ; le test relit la spécification Markdown, une table périmée échoue (`tests/spec_tables.rs`, `ci/gen_tables.py --check` en CI) ; `Column::logical` est renseigné d'après le format, puis l'informat, puis le type de stockage ;
  2. **50 fichiers non UTF-8** (latin1, wlatin1, Shift-JIS) lus avec texte identique aux CSV de SAS, 0 écart (`corpus_read.rs`) ; la table de **226 codes** d'encodage (225 nommés + code 0) donne l'encodage `encoding_rs` quand il en existe un (43 codes), sinon `None` (lecture en octets bruts) ;
  3. **dates** : `sas_days_to_ymd` reproduit le calendrier de SAS (pas de 29 février les années multiples de 4 000) : 29 dates `yymmdd10.` de l'oracle identiques, 9 valeurs hors 1582…20 000 rapportées `OutOfRange` ; 20 `datetime19.` et 16 `time8.` identiques (secondes arrondies, heures négatives et ≥ 24 h comprises) ; `sas_date_to_unix_days`, `sas_datetime_to_unix_micros`, `sas_time_to_micros` ;
  4. **octets invalides** (`enc_inv`) : `TextPolicy { invalid: Replace | Error | Binary, trim_trailing }` ; les 3 champs se relisent octet pour octet en `Binary`, sont comptés (3) en `Replace` et refusés (3) en `Error` ;
  5. **0 avertissement inattendu** sur les 232 fichiers : 34 fichiers portent des avertissements, tous attendus et versionnés dans `crates/uniformat-sas-io/tests/expected_warnings.tsv` (U24 sur les fichiers 32 bits, U22 sur les 6 fichiers datareader du jeu B, C09 sur 2 fichiers `readstat`, U20 sur la page `0x4000`, U19 sur `readstat/datetime`, U01 sur `pandas/many_columns`).
- Constats du J3 : (a) pour une date après l'an 4 000, `Date32 = valeur − 3 653` (spec) ne désigne pas le jour que SAS affiche (jusqu'à 5 jours d'écart en l'an 20 000) ; `sas_days_to_ymd` donne la date de SAS ; (b) `TextPolicy` et `RowRef::text_value` remplacent le `text()` provisoire de J1 (conservé comme commodité) ; (c) la sonde U22 ne contrôle que les 256 premières lignes ; (d) la plage maximale (20 000-12-31) est déduite de la spécification, seule la borne basse est vérifiée par l'oracle.
- Limite : le compteur d'octets invalides n'est pas dans `ReadReport` (l'appelant compte les `replaced`).

## J4 — Arrow et DataFusion

- Contenu : `uniformat-sas-arrow` (`arrow_schema`, `BatchReader`, missing spéciaux `Null`/`Sidecar`, métadonnées de champ), adaptateur `object-store` async, `uniformat-sas-datafusion` (`SasTableProvider`, projection, `LIMIT`, partitions par plages de pages, statistiques `num_rows`), `PagePlan` avec chemin rapide vérifié.
- ADR mises en œuvre : 0002, 0003, 0004.
- Critère de fin :
  1. `arrow_schema` d'un fichier de 5 000 colonnes obtenu en lisant **uniquement l'en-tête et les pages de métadonnées** (test qui compte les octets lus : ≤ `HL + nombre de pages de métadonnées × P`) ;
  2. requêtes DataFusion sur tout le corpus : `SELECT *`, `SELECT col`, `COUNT(*)`, `LIMIT n` donnent les mêmes valeurs que le lecteur Rust direct ; `COUNT(*)` = `row_count − deleted_count` sans lire les pages quand `Exact` ;
  3. lecture parallèle : résultat identique (à l'ordre près) pour 1, 4 et 8 partitions sur `taille_n50000` ;
  4. lecture par `object_store` (serveur local `object_store::local` et un serveur HTTP de test) : mêmes résultats, nombre de requêtes de plage borné (≤ 2 + nombre de groupes de pages) ;
  5. missing spéciaux : `x__missing` redonne les 28 codes de `valeurs_manquants_no`.
- Mesure : benchmarks de la stratégie de tests §6.5 de `docs/architecture.md`, premiers chiffres consignés (objectif : au moins égal à `pyreadstat` en lecture complète sur le même corpus ; si non atteint, tâche ouverte, pas de jalon manqué).

- **Réalisé le 2026-11-04** (`uniformat-sas-io` : `PagePlan`, `CountingSource` ; `uniformat-sas-arrow` : `arrow_schema`, `BatchAssembler`, `BatchReader`, `ObjectFile` ; `uniformat-sas-datafusion` : `SasTableProvider`, `SasExec`) :
  1. **schéma sans données** : le schéma Arrow de `taille_wide5000` (5 001 colonnes, 6 pages de métadonnées) se lit avec **737 792 octets ≤ HL + 6 × P = 860 160** ; l'ouverture respecte la borne `HL + pages de métadonnées × P` sur **les 232 fichiers** (l'en-tête de page de 40 octets est lu d'abord : une page de données n'est jamais lue, `tests/plan.rs`, `tests/corpus_batches.rs`) ;
  2. **SQL = lecteur direct** : sur les **232 fichiers**, `SELECT *`, `SELECT col` (première et dernière), `COUNT(*)` et `LIMIT 7` redonnent les valeurs du lecteur Rust direct (comparaison d'ensembles de lignes, 4 partitions) ; au niveau Arrow, **709 916 cellules** identiques au lecteur du cœur ; `COUNT(*)` sur `taille_n50000_no` (50 000 lignes) ne lit **aucune page de données** (serveur HTTP : 2 requêtes, `head` et préfixe, avant et après) ;
  3. **lecture parallèle** : 1, 4 et 8 partitions redonnent le même ensemble de lignes sur `taille_n50000_no` (plans à 1, 4, 8 partitions) et sur `suppression_n100_del10_no`, plan rapide comme plan complet ;
  4. **`object_store`** : magasin local et **serveur HTTP de test** (HEAD et `Range`) identiques à la lecture synchrone ; requêtes comptées côté serveur : **12 pour 10 groupes de pages** (= 2 + groupes), 13 pour 11 groupes avec 4 partitions, 9 requêtes pour 4 partitions SQL (borne 11) ;
  5. **missing spéciaux** : `x__missing` redonne les codes 1 à 28 de `valeurs_manquants_no` (`.`, `._`, `.A` à `.Z`), `x` est nul pour les 28, et `WHERE x__missing = 3` (`.A`) se filtre en SQL.
- Plan de pages (ADR 0002) : sur les **180 fichiers non compressés**, le plan rapide (pages de données supposées pleines, mesure de `rmax` sur la première page de données) n'est **contredit par aucune page** ; le plan complet et le plan rapide donnent les mêmes `rows_before`. Une page qui contredit le plan rapide rend `IoError::PlanMismatch` (« utiliser le plan complet ») ; `ReadOptions::plan = Full` lit l'en-tête de chaque page.
- Mesure : [`docs/benchmarks.md`](benchmarks.md) — `taille_n50000` : **1,6 ms** pour le driver (un fil, 31 M lignes/s ; 4 fils : 0,5 ms) contre **28 ms** pour `pyreadstat` (1,8 M lignes/s), soit ≈ 18× ; objectif atteint, avec les réserves du document (petits fichiers, cache chaud, `DataFrame` contre `RecordBatch`).
- Constats du J4 :
  (a) **DataFusion 55 dépend d'Arrow 59.2, pas 60** : `uniformat-sas-arrow` suit Arrow 59.2 (les types `RecordBatch` doivent être les mêmes) ; la mention « arrow 60 » du `Cargo.toml` (MSRV de J0) est corrigée ;
  (b) l'ouverture lit désormais l'en-tête de chaque page (40 octets) avant de lire le corps d'une page de métadonnées (sinon la première page de données était lue en entier) ;
  (c) **les tables compressées n'ont pas de plan découpable** : une seule partition, lues dans l'ordre (le nombre de lignes d'une page n'est pas dans son en-tête, `15` §2.1) ;
  (d) `num_rows` de DataFusion est `Exact` seulement sans ligne supprimée ; avec suppressions il reste `Inexact` (l'ADR 0004 admettait `Exact` pour le cas de bitmap observé ; non retenu faute de preuve par fichier avec le plan rapide) ;
  (e) `cargo deny` : licence `CC0-1.0` autorisée (`tiny-keccak`, via `arrow-array` → `ahash`), et la politique « graphe de production » est appliquée (`exclude-dev`) : le client HTTP des tests tire `quick-xml` 0.39, concerné par RUSTSEC-2026-0194 et -0195 ;
  (f) `PageDecoder` : `DecoderState` (état détachable), `PageHeader::parse_prefix`, `starting_at` ; `SasFile` partage ses métadonnées par `Arc`.
- Limites : (1) **options non réalisées** de l'ADR 0003 : `decimal_for_fixed`, `integers_when_exact`, `LargeUtf8` ; `sas.has_special_missing` vaut toujours `unknown` ; (2) lecture S3 réelle non testée (magasin local et serveur HTTP de test seulement) ; (3) un fichier dont les pages de données ne sont pas pleines échoue en plan rapide au lieu de se replier (`PlanMismatch`) : 0 cas dans le corpus ; (4) filtres non poussés (ADR 0004) ; (5) `criterion` non mis en place ; (6) CI hébergée non vérifiée.

## J5 — Python et R

- Contenu : `uniformat-sas-py` (PyO3, maturin, flux Arrow C Data vers pyarrow, conversions pandas et polars), `uniformat-sas-r` (extendr, `data.frame`, attributs `label`, `format.sas`, `informat.sas`, NA étiquetés), `uniformat-cli`.
- ADR mises en œuvre : 0003 (restitution Python/R), 0007 (erreurs et `unsafe` des FFI).
- Critère de fin :
  1. Python : sur le corpus, `read_sas` + `to_pandas()` redonnent les valeurs du CSV de référence ; `schema()` ne lit pas de page de données ; wheel `manylinux`/macOS construite par maturin dans la CI ;
  2. pandas/polars : `missing="sidecar"` conserve les 28 codes de manquants ;
  3. R : sur les fichiers du corpus lisibles par `haven`, valeurs égales (`all.equal`), attributs `label` et `format.sas` égaux ; les NA étiquetés se relisent avec `haven::na_tag()` (vérifie le motif de NaN décrit par `haven`, point ouvert de l'ADR 0003) ;
  4. une panique du cœur ne fait jamais tomber l'interpréteur Python ni R (tests avec fichiers corrompus du corpus de fuzzing) ;
  5. **c'est le premier jalon publiable** : la publication reste conditionnée à la décision NULL (ADR 0007).

- **Réalisé le 2026-11-04** (`uniformat-sas-py` : module natif `uniformat_io.sas._native` et paquet `python/uniformat_io.sas` ; `uniformat-sas-r` : conversion `convert` + glue extendr + paquet `rpkg` ; `uniformat-cli` : `sas7bdat info|schema|count|csv`) :
  1. **Python = CSV** : sur les **218 fichiers avec CSV de référence** (173 non compressés et 45 compressés), `read_sas_table(..., dates="float", missing="sidecar").to_pandas()` redonne les valeurs du CSV (tolérance `1e-13`, texte comparé octet pour octet dans l'encodage du fichier, codes de manquants comparés à `x__missing`) ; les 232 fichiers se lisent ou échouent par `SasError` ; `schema()` ouvre le fichier sous la borne `HL + pages de métadonnées × P` sur les 232 fichiers (sonde interne `_open_probe`), et un fichier tronqué est refusé (`SasFormatError`) ; la **wheel macOS arm64** (`cp39-abi3`) est construite par `maturin build --release`, installée dans un environnement vierge et passe les mêmes 11 tests pytest ;
  2. **manquants** : `missing="sidecar"` conserve les 28 codes (`x__missing` de `valeurs_manquants_no` = 1…28) en table Arrow, dans `df.attrs["sas_missing"]` (pandas : `"."`, `"_"`, `"A"`…`"Z"`), en `UInt8` ou `Categorical` (polars) ;
  3. **R = haven** : sur les **228 fichiers lisibles par `haven::read_sas`** (4 illisibles par `haven`, ReadStat échoue : `compression_type_0x02`, `0x06`, `0x09`, `0x0d`), valeurs égales (`all.equal`, `1e-12`), classes `Date` / `POSIXct` / `hms` égales, `label` et `format.sas` égaux, étiquettes de NA égales ; les **28 manquants** se relisent avec `haven::na_tag()` (`""`, `"_"`, `"a"`…`"z"`) et un NA construit par `haven::tagged_na("b")` donne la même étiquette que le nôtre ;
  4. **pas de plantage** : 60 fichiers × 12 altérations (troncatures, octets aléatoires, en-tête) = **720 fichiers corrompus** × 2 appels en Python, **480** en R : uniquement `SasError` / `OSError` / `ValueError` côté Python, `sas7bdat_error` côté R ; aucune `PanicException`, aucune erreur interne, l'interpréteur reste vivant ;
  5. **publication** : inchangée, le premier jalon publiable reste conditionné à la décision NULL (`publish = false`, classifieur `Private :: Do Not Upload`).
- CLI : `sas7bdat count` (sans lire de page de données), `info` (texte ou `--json`), `schema`, `csv` (`--columns`, `--limit`, `--missing sidecar`, `--dates raw`) ; test sur le corpus : 50 000 lignes comptées, CSV des 200 premières lignes égal au CSV de référence, 28 codes de manquants.
- Constats du J5 :
  (a) **`haven` rend `.A` à `.Z` avec les étiquettes minuscules `a` à `z`** (ReadStat) ; le paquet R fait de même (l'exemple `tagged_na("B")` de l'ADR 0003 devient `tagged_na("b")`), `._` reste `"_"`, `.` est `NA_real_` ; le motif est celui de R (`NA_real_` = NaN de mot bas 1954, étiquette en octet 4 little endian), vérifié par `haven::na_tag()` dans les deux sens ;
  (b) **R n'accepte pas de NUL dans une chaîne** : un champ texte contenant un NUL (`compression_runs_*`) faisait échouer extendr (« embedded nul in string ») ; le texte est coupé au premier NUL avec un avertissement ;
  (c) **écarts documentés avec `haven`** (encodés dans le test) : `haven` ne masque pas les lignes supprimées (100 lignes contre 90 pour `suppression_n100_del10_*`, 5 contre 3 pour `readstat/datetime`) alors que le bitmap de suppression est appliqué ici ; pour les fichiers issus de `PROC IMPORT` (`datareader`, `pandas`) `haven` rend `format.sas` sans la largeur (`BEST`, `$`, `MMDDYY`) alors que le fichier la porte (`BEST12`, `$9`, `MMDDYY10`, conforme à `make.sas`) ; octets invalides de `compression_runs_*` : U+FFFD ici, octets gardés par `haven` ;
  (d) **incohérence à trancher** : `classify_format` retombe sur l'**informat** quand la colonne n'a pas de format, donc Arrow et Python rendent `Date32` / `Timestamp` / `Time64` pour `metadonnees_infmt_date9_*`, `_datetime19_*`, `_time8_*` alors que SAS affiche la valeur brute et que `haven` rend un `numeric` ; le paquet R suit le format seul (comme `haven`), Arrow et Python restent inchangés (décision J3) ;
  (e) `cargo deny` : licence `BSD-2-Clause` autorisée (`numpy`, via `pyo3-arrow`) et avis `RUSTSEC-2024-0436` (`paste`, non maintenu, macros de compilation tirées par `extendr-api`) ignoré avec sa raison dans `deny.toml` ;
  (f) `pyo3` 0.30 (`abi3-py39`) et `pyo3-arrow` 0.20 (Arrow 59) ; le flux sort par l'interface PyCapsule `__arrow_c_stream__`, `pyarrow >= 15` le relit (`RecordBatchReader.from_stream`) ; `uniformat-sas-py` reste en `#![deny(unsafe_code)]` sans aucun bloc `unsafe` écrit ici, `uniformat-sas-r` n'autorise `unsafe` que dans le module `glue` généré par extendr (feature `r`) ; sans cette feature la crate se compile et se teste sans R ;
  (g) le `Makevars` du paquet R doit lancer `cargo build` à chaque installation (une règle `make` sans dépendance ne reconstruisait pas la bibliothèque statique) ; `CARGO_TARGET_DIR` est respecté (le volume du projet n'a pas de verrouillage de fichiers).
- Limites : (1) Python : **chemins locaux seulement** (une URL rend `SasUnsupportedError`), `write_sas` arrive en J6, les avertissements de lecture ne sont émis que par `read_sas_table` et ses dérivés (le flux paresseux n'émet que ceux de l'ouverture) ; (2) R : `col_select` par noms (pas de `tidyselect`), `write_sas7bdat` arrive en J6, paquet construit depuis le dépôt (pas de vendoring pour CRAN), `R CMD check` non lancé ; (3) la **wheel `manylinux`** (seule la wheel macOS a été construite) et la CI hébergée (jobs `python` et `r-package`) n'ont **pas tourné** ; (4) fuzzing `cargo-fuzz` toujours non exécuté (nightly absent) : le critère 4 repose sur des altérations aléatoires reproductibles (graine fixe), pas sur du fuzzing guidé ; (5) l'écart d'informat (d) reste ouvert.

## J6 — Écriture

- Contenu : `WriteSchema::validate`, `FileBuilder`, `SasWriter`, `ArrowWriter`, écriture non compressée (`20` §4.1), compressée `Char`/`Binary` (§4.2, W01, W02 et W11 résolues), valeurs non représentables (ADR 0005), liaison Python (`write_sas`) et R (`write_sas7bdat`).
- ADR mises en œuvre : 0005, 0006 (W01–W09, U-écriture), 0007.
- Critère de fin :
  1. la **matrice de `rea_output/tools/write_matrix.md`** (49 cas) est rejouée avec le **driver** à la place de `ref_writer.py` : relue par le driver, pandas, pyreadstat, Parso, ReadStat, et — suite optionnelle — SAS 9.4M7 (`sas_small`) : **0 KO inattendu**, les 9 « KO connus » restent des assertions négatives ;
  2. round-trip `proptest` Arrow → fichier → Arrow sans perte pour les types supportés ;
  3. limites de `20` §8 : chaque dépassement (nom 33 octets, label 257 octets, colonne 32 768 octets, trop de colonnes) renvoie l'erreur typée **avant le premier octet** pour les limites de schéma ;
  4. octets écrits comparables à ceux de SAS : `diff_recopies` rejoué sur le driver, 0 plage non expliquée ;
  5. écriture transactionnelle : aucun fichier partiel après une erreur (test d'injection).
- Reste ouvert (non bloquant) : seuil de longueur de ligne de la compression (C02, 25 à 27 octets), métadonnées sur plusieurs pages (W04), `ColumnList` (W05). W01, W02, W11 sont résolues (2026-11-02).

- **Réalisé le 2026-11-04** (`uniformat_sas::write` : `FileBuilder`, `WriteSchema`, `WriteOptions`, `CellValue`, `SchemaError`, `WriteError`, `WriteReport` ; `uniformat-sas-io` : `SasWriter`, `AtomicFile` ; `uniformat-sas-arrow` : `ArrowWriter`, `write_batches`, `infer_char_lengths` ; `uniformat-sas-py` : `write_sas` ; `uniformat-sas-r` : `write_sas7bdat`) :
  1. **matrice rejouée avec le driver** (`rea_output/tools/validate_write_driver.py` ; résultat `rea_output/tools/write_matrix_driver.md`) : les **57 cas** de `write_cases.py` sont écrits par `uniformat_io.sas.write_sas` à la place de `ref_writer.py` et relus par le driver, pandas 2.3.3, pyreadstat (ReadStat), Parso 2.0.14 et `ref_reader.py` : sur 285 cellules, **262 OK, 0 KO inattendu**, 1 KO connu (pyreadstat refuse le code d'encodage 29, `w12_latin1`), 15 « refusé » (`w14_name33`, `w14_label257`, `w14_char32768` : le driver renvoie l'erreur typée avant d'écrire et ne laisse aucun fichier), 2 non applicables (dates dans Parso), 5 non faisables (`w15_gt2gb`). **SAS (`sas_small`) n'a pas été exécuté** (oracle Docker indisponible ici) : la suite optionnelle reste à rejouer. Les fichiers du driver sont **identiques octet pour octet** à ceux de `ref_writer.py` (mêmes entrées, même code de fichier, même date) pour **52 des 53 cas écrits par les deux** ; le 53e, `w13_page1024`, est refusé par `ref_writer.py` (métadonnées trop grandes pour 1 024 octets) et écrit par le driver avec une page agrandie à 2 048 (ADR 0005 §3) ;
  2. **aller-retour Arrow → fichier → Arrow** : **687 aller-retour** (229 fichiers du corpus relus, réécrits en plat, `CHAR` et `BINARY`, relus : colonnes, sidecars et types identiques ; 3 fichiers non réécrits : colonnes `Binary` d'encodage sans équivalent) et `proptest` (64 tables aléatoires × 3 modes : flottants, dates, textes accentués, microsecondes, codes de manquants) sans perte ;
  3. **limites avant le premier octet** : nom de 33 octets, label de 257, colonne caractère de 32 768 (et de 0), numérique de 2 octets, nom en double, aucune colonne, trop de colonnes sans agrandissement de page (700 pour `P = 65 536`) renvoient `SchemaError` / `SasWriteError` / condition R **avant toute création de fichier** (tests Rust, Python, R et matrice) ; avec `grow_page` (défaut) la page passe à 131 072 pour 700 colonnes ;
  4. **`diff_recopies` rejoué sur le driver** (`DIFF_WRITER=driver`, 13 fichiers du corpus dont CHAR et BINARY) : **0 plage non expliquée** (`rea_output/evidence/write/diff_recopies_driver.txt`) ;
  5. **écriture transactionnelle** : fichier temporaire du même dossier renommé à `commit` ; une erreur de valeur en cours d'écriture, un schéma invalide ou un abandon ne laissent **ni fichier ni temporaire**, et un fichier existant n'est pas touché par une écriture qui échoue (tests Rust, Python et R).
- Constats du J6 :
  (a) **ReadStat refuse les copies RDC qui recouvrent leur propre source** (`longueur > décalage`) : un flot valide pour pandas, Parso et le lecteur du projet faisait échouer `pyreadstat` / `haven` (« Error parsing page 0 »), constaté par le test R d'écriture relu par `haven` sur une ligne de 58 octets. L'encodeur `rdc_compress` du cœur ne produit plus de copie recouvrante (`len < offset`) ; propriété testée par un décodeur aux règles de ReadStat (8 000 flots). La matrice de départ ne l'avait pas révélé (aucun cas ne déclenche le recouvrement) ;
  (b) **pandas 3.1.0 refuse les tables compressées à 0 ligne** (`AssertionError: Out of bounds read`, `w11_char_zero` et `w11_binary_zero`) ; pandas 2.3.3, la version de la matrice d'origine, les lit, et les octets sont identiques à ceux de `ref_writer.py` : la matrice de ce jalon est donc rejouée avec pandas 2.3.3 ; à surveiller côté pandas ;
  (c) **le cœur reproduit `ref_writer.py` à l'octet près** (port de §4 de `20`), y compris la valeur du champ libre « décalage du pointeur terminal » des pages compressées (`32 + 24 × pointeurs`), qui n'est pas celle de la spec (`40 + 24 × sc`) mais que SAS ignore (champ `libre`, `20` §5.3) ;
  (d) la **page marqueur** `0x9000` ne contient que `A − 48` octets d'enregistrements (`A = min(P, 32 767)`, 18 octets par page de lignes) : une table compressée de plus de **1 800 pages de lignes** (≈ 115 Mio compressés à 64 Kio la page) est refusée (`WriteError::Unsupported`) ; le comportement de SAS au-delà (plusieurs pages marqueur ?) n'est pas connu (nouvelle inconnue **W12**) ;
  (e) valeurs non représentables : `Error` par défaut, `Replace` (`?` pour un caractère non encodable, `.` pour ±Inf, arrondi pour un entier de plus de 53 bits ou un décimal inexact, troncature de poids faible pour une longueur numérique < 8), `Truncate` (texte coupé à la limite d'un caractère, jamais au milieu), tous comptés dans le rapport ; `NaN` s'écrit `.` ; un texte nul s'écrit en blancs ; le texte vide et le manquant caractère ne se distinguent pas à la relecture (SAS ne les distingue pas) ;
  (f) Python : les longueurs des colonnes caractère sont mesurées sur les données quand elles ne sont pas fournies (`lengths=` ou métadonnée `sas.length`), ce qui lit le flux en mémoire ; un DataFrame lu par `read_sas_pandas` se réécrit avec ses labels, ses formats et ses manquants spéciaux (`df.attrs`) ; R : les NA étiquetés de `haven` redeviennent `._` et `.A` à `.Z` (étiquettes minuscules ou majuscules).
- Limites : (1) **SAS lui-même n'a pas relu** les fichiers du driver dans cette session (oracle absent) : les 57 cas ont été relus par le driver, pandas, ReadStat, Parso et `ref_reader.py` ; la relecture par SAS 9.4M7 reste la suite optionnelle (`SAS7BDAT_SAS_ORACLE=1`) ; (2) `Compression::Auto` de l'ADR 0005 n'est pas réalisée (le choix est explicite : `none`, `char`, `binary`) ; (3) le **label de table** n'est pas écrit (seul le nom de table l'est, octets 92 à 123) ; (4) les noms de colonne ne sont pas contrôlés contre les règles de nom SAS (lettres, chiffres, soulignement) : seules les limites de longueur et d'encodage le sont ; (5) métadonnées sur plusieurs pages (W04) et `ColumnList` (W05) non écrits ; au plus 4 000 colonnes ; (6) 64 bits little endian seulement, encodages 20, 29, 62 ; ni lignes supprimées, ni index, ni chiffrement ; (7) `Unrepresentable::Replace` sur les dates hors plage rend un manquant ; (8) fichier de plus de 2 Go (W08) non essayé ; (9) `criterion` et fuzzing de l'écrivain non faits (le fuzzing n'a jamais été exécuté faute de nightly) ; (10) CI hébergée non vérifiée.

## J7 — Arrow Flight / connecteur type Dremio

- Contenu : `uniformat-sas-flight` : `GetFlightInfo` (schéma seul, `FlightEndpoint` par groupe de pages), `DoGet(ticket)` (fichier + plage de pages + projection + `LIMIT`), listing de fichiers, authentification déléguée ; lecture distribuée par plages de pages (ADR 0002 et 0004).
- ADR mises en œuvre : 0002, 0004.
- Critère de fin :
  1. un client Flight (`pyarrow.flight`) obtient le schéma **sans** transfert de données (octets lus ≤ jalon 4, critère 1) ;
  2. la lecture des N endpoints en parallèle redonne les mêmes lignes que la lecture directe (comparaison d'ensembles) sur `taille_n50000` et sur un fichier compressé ;
  3. un connecteur Dremio (hors dépôt) lit un fichier du corpus via le service Flight (validation manuelle consignée) ;
  4. benchmark Flight local : débit mesuré et consigné (aucun seuil annoncé avant mesure).

- **Réalisé le 2026-11-04** (`uniformat-sas-flight` : `SasFlightService`, binaire `uniformat-sas-flight-server`) :
  1. **schéma sans données** : `GetFlightInfo` n'ouvre que l'en-tête et les pages de métadonnées ; octets lus ≤ `HL + pages de métadonnées × P` (J4, critère 1) et égaux à ceux d'une ouverture seule, `data_bytes = 0` avant tout `DoGet` (test Rust sur `taille_n50000_no/char` et une table compressée ; compteurs lus par l'action `stats` depuis `pyarrow.flight`). `GetSchema` rend le même schéma (projection comprise) ;
  2. **endpoints parallèles = lecture directe** : un `FlightEndpoint` par groupe de pages (plan de l'ADR 0002) ; sur `taille_n50000_no` et `taille_n50000_char` (4 endpoints, lus en parallèle par 4 clients) et sur un fichier compressé (un seul endpoint : la table compressée n'est pas découpable, J4 (c)), la concaténation redonne exactement les colonnes de la lecture directe ; même résultat avec un vrai client **`pyarrow.flight`** (threads) ; `LIMIT` (un endpoint, exact), projection et `x__missing` (28 codes) traversent Flight ;
  3. **connecteur Dremio** : **non réalisé** (hors dépôt, validation manuelle impossible ici) ; le service est un serveur Flight standard (`GetFlightInfo` avec `FlightEndpoint` sans localisation = même serveur, `DoGet(ticket)`), à valider sur un Dremio réel ;
  4. **benchmark local** ([`docs/benchmarks.md`](benchmarks.md), `benches/bench_flight.py`) : table de 2 M lignes (80,4 Mo écrits par le driver), localhost, 5 répétitions : lecture directe 20,7 M lignes/s ; Flight 1 endpoint 20,0 M lignes/s ; **4 endpoints 30,9 M lignes/s** (≈ 1,1 Go/s Arrow) ; 8 endpoints 31,8 ; `GetFlightInfo` (schéma + 4 endpoints) 0,24 ms. Aucun seuil annoncé avant mesure.
- Fonctions : `GetFlightInfo` (descripteur `PATH` ou `CMD` JSON : fichier, `partitions`, `columns`, `limit`, `missing`, `dates`, `encoding`, `trailing_blanks`, `plan`, `batch_rows`), `GetSchema`, `DoGet(ticket)`, `ListFlights` (tous les fichiers du dossier, schéma et nombre de lignes, sans endpoint ; filtre par sous-chaîne), action `stats`, jeton porteur optionnel (`--token` ou `UNIFORMAT_FLIGHT_TOKEN`, intercepteur `authorization: Bearer …`) ; lecture seule (`DoPut`, `DoExchange`, `PollFlightInfo` refusés).
- Constats du J7 :
  (a) **le ticket revient d'un client : tout est revalidé à `DoGet`** (chemin relatif confiné au dossier racine par `canonicalize`, ni `..`, ni chemin absolu, ni lien sortant, extension `.sas7bdat`, plage dans le fichier, `rows_before` et nombre de lignes recalculés par le plan, jamais lus du ticket, plage partielle refusée pour une table compressée) ; tickets forgés testés ;
  (b) **les fichiers sont lus par un `FileSource` synchrone** dans des tâches bloquantes (`spawn_blocking`) avec un canal borné de 4 lots : un client lent bloque la lecture (contre-pression) ; l'adaptateur `ObjectFile` de J4 n'est pas utilisé car il lit un préfixe de 1 Mio à l'ouverture, ce qui dépasserait la borne du critère 1 pour les petits fichiers ;
  (c) `arrow-flight` 59.3 va avec `tonic` 0.14 et Arrow 59 ; `cargo deny` : aucune licence ni avis nouveau ;
  (d) `total_records` vaut `row_count − deleted_count` (exact seulement sans ligne supprimée, comme `num_rows` de DataFusion, ADR 0004).
- Limites : (1) **dossier local seulement** (pas d'`object_store`, pas de S3) ; (2) **pas de TLS ni d'authentification mutuelle** : jeton porteur en clair sur gRPC, à placer derrière un proxy TLS ; (3) pas d'`ordered = false` : les endpoints sont ordonnés ; (4) pas de `FlightEndpoint` multi-serveurs (aucune localisation émise) ; (5) tables compressées en un seul endpoint ; (6) pas de reprise (`PollFlightInfo`) ni d'écriture (`DoPut`) ; (7) `ListFlights` ouvre chaque fichier (en-tête et métadonnées) : 196 fichiers listés sans erreur, plafonné à 10 000 ; (8) benchmark sur une machine, en localhost, sans réseau réel ni concurrence de clients ; (9) CI hébergée non vérifiée (jobs `python` : test `pyarrow.flight` avec le binaire construit).

## Risques transverses

- **Spécification partielle** : aucune entrée `confirmé` ; un jalon peut révéler un écart que seule la décompilation ou le SAS complet résoudrait. Procédure : ouvrir la correction dans la spécification (changement amont), pas dans le code seul.
- **Calendrier NULL** : confirmation de licence et publication, hors contrôle.
- **Performance** : le format est orienté ligne et sans statistiques ; les gains par rapport aux lecteurs existants viendront de la projection, du parallélisme et de l'absence d'allocation par valeur, pas du filtrage.
